# F310 知識ベースの更新

公式サイトと手元の知識ベース（KB）を突き合わせ、必要なら取り直す。
コマンドは必ず次の形で、1行を1回のBash呼び出しとして実行する（シェル変数は呼び出しをまたいで残らない）。

引数: `$ARGUMENTS`（`check` なら手順2で終える）

## 1. 更新の有無を調べる

先に「公式サイトに問い合わせて確認する（1〜2分）」と一言伝えてから実行する。
公式サイトへは1秒間隔で、マニュアル16冊に HEAD、設定例56ページに GET を送る。KBの中身には書き込まない。

```bash
F310_KB_DIR="${CLAUDE_PLUGIN_DATA}" python3 "${CLAUDE_PLUGIN_ROOT}/scripts/build.py" --check-updates
```

Bash のタイムアウトは 300000 ミリ秒にする。終了コードは、更新が要らなければ 0、何かあれば 1。

## 2. 結果を読んで伝える

出力末尾の `== 結果 ==` の「公式サイト」「手元のKB」の2行で判断する。

| 結果 | やること |
|---|---|
| 公式サイトは変わっておらず、手元のKBも最新 | 「最新です」と伝えて終える。取得はしない |
| 手元のKB: 知識ベースが未構築 | 初回構築になる。約48MB（マニュアルPDF16冊＋設定例56ページ）を取得し数分かかる、と伝えて手順3へ |
| 手元のKB: 公式サイトより古い | `OLD` の行を要約して伝える（どのマニュアルが古いか、設定例が何件違うか、索引が旧形式か）。手順3へ |
| 公式サイト: 検証した版より新しいものがあり、手元のKBは取り込み済み | 手元のKBは公式サイトと同じなので取得は要らない、と伝えて終える。このプラグインでは未検証の版なので、プラグイン自体の更新で検証済みの版が届くことがある、と添える |
| 公式サイト: 検証した版より新しいものがあり、手元のKBは古い | `CHANGED` / `NEW` の行を要約して伝える。取り込めるが、このプラグインでは未検証の版なので、構築の最後に件数の注記が出ることがある、と添える。プラグイン自体の更新（検証済みの版が入っていることがある）も選択肢として伝える。手順3へ |
| 公式サイト: 取得できないものがある（`BROKEN` / `GONE`） | ネットワークの不調か公式サイトの構成変更。取り直しはせず、該当の行を伝えて終える |

引数が `check` なら、ここで終える（取り直しはしない）。

## 3. 了承を得てから取り直す

**取得の前に必ず利用者の了承を得る。** 何を取り直すか（手順2の要約）と、数分かかることを伝えて確認する。
PDF は更新された冊だけを取り直し、設定例は全56ページを確認して本文が変わったものだけを取り直す。

了承が得られたら実行する。Bash のタイムアウトは 600000 ミリ秒にする。

```bash
F310_KB_DIR="${CLAUDE_PLUGIN_DATA}" python3 "${CLAUDE_PLUGIN_ROOT}/scripts/build.py"
```

`mutool` が無いと止まる（`brew install mupdf-tools`）。

## 4. 結果を伝える

出力末尾の `== 結果 ==` 以降を要約して伝える。

- ページ数・コマンド数・設定例の件数
- 「網羅性チェック OK」と「検索回帰 N/N 件成功」が出ていれば、更新は完了
- 「手元の版が検証済みの版と違う箇所があります」「版違いでページがずれた可能性」は、未検証の新しい版を
  取り込んだときに出る**想定どおりの注記**。検索には使える、と伝える
- `⚠ 想定値と一致しません` が出たら、その下の行をそのまま伝える。取得の失敗ならネットワークを確認して
  もう一度 `/f310-kb:update` を、抽出の退行が疑われるならプラグインの作者への報告を勧める

## してはいけないこと

- 了承を得ずに手順3を実行する
- `--force`（全部の取り直し）・`--prune-pdf`（PDFの削除）・`--accept-current`（保守者向け。プラグイン内のファイルを書き換える）を使う
- KB のディレクトリを削除・移動する
